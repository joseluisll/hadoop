# HBase 2.5.16 binary-tarball license audit (peer comparator, T00031)

Date: 2026-11-12
Purpose: turn the peer-release-comparator claim ("HBase generates
LICENSE.txt from POM metadata and never verifies it against the shipped
jar population") into a measured number, using our own archive
enumerator as ground truth. Evidence for the HADOOP-20078 comparison
package.

## Method

- Official published tarball `hbase-2.5.16-bin.tar.gz` from
  downloads.apache.org, sha512 verified against the published digest.
  Never a local build.
- `enumerate-archive-jars.py` (our enumerator, unmodified) over the
  exploded tree: 324 jars.
- Partial rows (empty group) resolved WITHOUT Central search (it
  rate-limits this host): first from the jars' embedded
  META-INF/maven metadata (58 rows), the rest via repo1.maven.org POM
  probes where a candidate group was accepted only if the POM exists at
  that path AND its `<artifactId>` matches (verified, not assumed).
  Result: 304 distinct third-party+own coordinates, 0 unresolved rows.
- Licenses: each coordinate's own POM from repo1, parent-chain fallback
  (up to 6 hops; Apache-Directory chains need 5, Hadoop YARN 4 — the
  original 3-hop limit produced 36 false "no license" rows).
- Acknowledgment check: non-ALv2 coordinates matched against
  LICENSE.txt by POM `<name>` (fallback artifactId), lowercased,
  parentheticals stripped — plus manual adjudication of every flagged
  row against the actual section text.

## Numbers (provenance: this audit's verified artifacts)

- 324 shipped jars -> 304 distinct g:a:v coordinates.
- 72 HBase/Hadoop-own coordinates (excluded from third-party checks).
- 179 third-party coordinates ALv2 per their POMs (blanket-covered by
  the file's Apache license header — not individually checked).
- 51 third-party coordinates non-ALv2 per their POMs; 44 acknowledged
  in LICENSE.txt sections; 7 flagged, of which manual adjudication
  leaves 3 unacknowledged, 1 era-mismatched, 3 covered by
  family-level section entries.

## Deviation findings

1. Unacknowledged non-ALv2 jars (3):
   - `antlr:antlr:2.7.7` (BSD) — no antlr mention anywhere in
     LICENSE.txt.
   - `javax.ws.rs:jsr311-api:1.1.1` (CDDL) — jar is "JAX-RS: Java API
     for RESTful Web Services"; no jsr311/jax-rs/restful mention in any
     section.
   - `com.sun.xml.bind:jaxb-impl:2.3.9` (EDL-1.0) — the EDL section
     lists 14 works, no JAXB implementation among them; the CDDL
     section's 2010 GlassFish entry is a different license era.
2. Era-mismatched acknowledgment (1):
   - `javax.xml.bind:jaxb-api:2.3.1` — covered only by "JAXB API bundle
     for GlassFish V3, Copyright (c) 2010 Oracle" in the CDDL 1.1
     section; the shipped jar is Oracle's 2.3.1 build (manifest:
     Bundle-Name jaxb-api, Implementation-Vendor Oracle Corporation).
     Curator judgment needed on whether the entry is the same work.
3. Stale bundled-works version claim (1):
   - LICENSE.txt ("Apache HBase - Server contained works") states
     jquery "version 1.8.3", "Copyright 2012 jQuery Foundation"; the
     shipped `hbase-webapps/static/js/jquery.min.js` is
     "jQuery v3.7.1 | (c) OpenJS Foundation". Both the version and the
     copyright holder are stale.
4. Unacknowledged vendored web assets (2):
   - `hbase-webapps/static/js/bootstrap.bundle.min.js` (MIT) and
     `hbase-webapps/static/js/jquery.tablesorter.min.js` (MIT) ship
     with no matching entry in LICENSE.txt (no bootstrap/tablesorter
     mention anywhere). jquery and vega in the same directory ARE
     covered; these two are not.
5. No ghost sections: every bundled work the file describes (jruby,
   commons-math3, netty, vega, orca, thrift-era entries) was verified
   to ship. The drift in HBase's file runs the other way — things ship
   unlisted — not sections pointing at nothing.
6. POM-no-license corpus, kept separate per the audit recipe (these
   indicate the project's supplemental-models curation, not drift):
   `asm:asm:3.1` (its whole POM chain declares no license) and
   `com.sun.xml.ws:policy:2.7.10` (malformed POM, unbound prefix) —
   both are acknowledged in LICENSE.txt by name.
7. Coordinate-form quirks in the enumeration input (our side, not
   HBase's): manifest-derived names drift from POM casing (Agrona,
   ASM, Objenesis), one version split at a dash+digit boundary
   (geronimo-jcache_1.0_spec 1.0-alpha-1), one version field carries a
   build stamp (ehcache 3.3.1). All corrected and recorded in the
   audit's group-map; none affects the findings above.

## Comparator takeaways for HADOOP-20078

- HBase's generation is genuinely fail-closed on METADATA (the build
  demands license info per dependency, curated via
  supplemental-models) — established ASF practice, matching our
  proposal's framing.
- But the shipped file still drifted in exactly the classes our system
  detects mechanically: 3 unacknowledged non-ALv2 jars, 1 stale
  version+copyright claim, 2 unacknowledged vendored assets, 0 ghost
  sections. None of these is discoverable from POM metadata; all are
  discoverable from the tarball itself with our enumerator + mention
  check.
- The audit ran with ZERO HBase source-tree access and no HBase build:
  published tarball + public POM data only. That is the trust story for
  the proposal: verification needs only the artifact a voter already
  has.

## Reproducibility

All inputs and scripts preserved (24h-scratch — re-download the
tarball if pruned; the TSV, group-map, POM cache and analysis scripts
are small): `~/.hermes/cache/scratch/hbase-audit/` —
hbase-jars.tsv (our enumerator's output), group-map.json (verified
group resolutions), pom-licenses.json (POM license corpus with
resolved_from provenance), resolve-groups.py, verify-groups.py,
fetch2.py, analyze.py, analyze-out.txt.

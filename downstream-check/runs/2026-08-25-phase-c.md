## Rung 1 — API signatures

Filtered to `InterfaceAudience.Public` and `LimitedPrivate`, with
`--keep-internal`. 90 jars per side.

**Result: 18 binary and 18 source compatibility problems, 99.9% compatible.**
They fall into two groups, plus one artefact of the run itself.

### 1. `ContainerShellWebSocket` — 16 methods, real

`@InterfaceAudience.LimitedPrivate({"HDFS","MapReduce","YARN"})`,
`@InterfaceStability.Unstable`, in two classes:

- `org.apache.hadoop.yarn.client.api.ContainerShellWebSocket`
- `org.apache.hadoop.yarn.server.nodemanager.webapp.ContainerShellWebSocket`

Every method taking a websocket `Session` changed parameter type from Jetty 9's
`org.eclipse.jetty.websocket.api.Session` to Jetty 12's
`org.eclipse.jetty.ee8.websocket.api.Session`. The checker reports 16 removed
methods and 16 added methods — the methods were replaced, not deleted.

Assessment: **expected and probably acceptable.** The class is a websocket
handler whose signature has always named a Jetty type, so it could not survive a
Jetty major upgrade unchanged. It is LimitedPrivate to HDFS/MapReduce/YARN, and
its signature already leaked a shaded Jetty type before this change. Worth
stating on HADOOP-19972 rather than leaving for someone to find.

### 2. `HttpServer2.webAppContext` — one field, worth attention

> Type of field `webAppContext` has been changed from
> `org.eclipse.jetty.webapp.WebAppContext` to
> `org.eclipse.jetty.ee8.webapp.WebAppContext`.
> A client program may be interrupted by `NoSuchFieldError`.

Reached through `org.apache.hadoop.yarn.webapp.WebApp.getHttpServer()` and
`WebApp.httpServer()`, which return `HttpServer2`.

Assessment: **this is the one to look at.** `HttpServer2` is the class the issue
names as marked Private but used across the ecosystem — Ozone embeds it in
`BaseHttpServer`. Any downstream code reading that field directly gets
`NoSuchFieldError` at runtime, not a compile error, which is exactly the failure
mode rung 1 exists to catch early.

### 3. `org.eclipse.jetty.server.Server` superclass — an artefact, not a finding

Reported as a Medium data-type problem: superclass changed from
`handler.HandlerWrapper` to `Handler.Wrapper`. That is Jetty's own API change,
visible only because `hadoop-benchmark-3.6.0-SNAPSHOT-uber.jar` bundles Jetty
unshaded, and `--include-file 'hadoop.*'` matched the uber jar by name.

**Method note:** upstream's `find_jars` excludes `-tests`, `-sources` and
`-with-dependencies`, but not `-uber`. Any run should add
`--exclude-file '.*-uber\.jar'`, or it analyses third-party classes as though
they were Hadoop API.

## Checker version

`japi-compliance-checker` 2.4, the latest release, **fails under JDK 21** with
`ERROR: internal error in parser` — on a two-class toy jar as well as on
hadoop-common, so it is not Hadoop-specific. 2.0 through 2.3 work.

On hadoop-common 3.4.0 → 3.4.1, versions 1.8 and 2.3 report identical results
(1 binary problem, 2 warnings, 99.98%); 2.3 takes 28 s against 1.8's 62 s.

Recommendation: **2.3**. Hadoop's own script pins 1.8, but the harness records
the version it used, so reproducibility does not depend on matching that pin.
Reaching for "latest" would have produced nothing.

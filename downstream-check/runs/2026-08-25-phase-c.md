## Rung 1 — API signatures

Filtered to `InterfaceAudience.Public` and `LimitedPrivate`, with
`--keep-internal`, over **86 jars per side**. Four jars are excluded:

```
--exclude-file 'hadoop-client-api-.*'          # repackages the whole API
--exclude-file 'hadoop-client-runtime-.*'
--exclude-file 'hadoop-client-minicluster-.*'
--exclude-file '.*-uber\.jar'                  # bundles Jetty unshaded
```

The three shaded client jars are repackaged copies of classes already compared
unshaded, so including them double-counts every finding and attributes it to a
jar that does not own the source. Rung 2 covers the shaded artifacts, which is
its job. The benchmark uber jar bundles Jetty itself, so including it makes the
checker analyse third-party classes as though they were Hadoop API. Upstream's
`find_jars` excludes `-tests`, `-sources` and `-with-dependencies`, but none of
these.

Run time: 27 minutes. The unfiltered 90-jar comparison took about 64.

**Result: 9 binary and 9 source compatibility problems, 99.9% compatible.**

### 1. `ContainerShellWebSocket` — 8 methods. Expected.

`@InterfaceAudience.LimitedPrivate({"HDFS","MapReduce","YARN"})`,
`@InterfaceStability.Unstable`, in two classes:

| Jar | Class |
| --- | --- |
| `hadoop-yarn-client` | `org.apache.hadoop.yarn.client.api.ContainerShellWebSocket` |
| `hadoop-yarn-server-nodemanager` | `org.apache.hadoop.yarn.server.nodemanager.webapp.ContainerShellWebSocket` |

Every method taking a websocket `Session` changed parameter type from
`org.eclipse.jetty.websocket.api.Session` to
`org.eclipse.jetty.ee8.websocket.api.Session`. 8 removed, 8 added — replaced,
not deleted.

Assessment: **expected, and hard to avoid.** These are websocket handlers whose
signatures have always named a Jetty type, so they cannot survive a Jetty major
upgrade unchanged. LimitedPrivate to HDFS/MapReduce/YARN. Worth stating on
HADOOP-19972 rather than leaving to be discovered.

### 2. `HttpServer2.webAppContext` — reported, but not reachable downstream.

In `hadoop-common`, `org.apache.hadoop.http.HttpServer2`:

> Type of field `webAppContext` has been changed from
> `org.eclipse.jetty.webapp.WebAppContext` to
> `org.eclipse.jetty.ee8.webapp.WebAppContext`.
> A client program may be interrupted by `NoSuchFieldError`.

Assessment: **not a downstream break.** The declaration is
`protected final WebAppContext webAppContext`, which looks reachable, but the
enclosing class is:

```java
public final class HttpServer2 implements FilterContainer {
  private HttpServer2(final Builder b) throws IOException {
```

`final`, with a single private constructor. Nothing outside
`org.apache.hadoop.http` can subclass it, so `protected` grants no access to any
downstream code; effectively the field is package-private. The only classes that
could hit `NoSuchFieldError` are Hadoop's own, in that package, which are
recompiled together.

The checker cannot see this. It is handed `javap -s -private` output and reports
every member whose type changed, without reasoning about whether the enclosing
class can be extended or instantiated from outside.

**So rung 1 finds no downstream-reachable signature break in phase-c.** The
`ContainerShellWebSocket` changes are reachable — that class is a plain
`public class` with a public no-arg constructor — but it is LimitedPrivate and
Unstable, and its signature has always named a Jetty type.

This is worth carrying into rung 1's method: a reported field or method on a
`final` class with no accessible constructor deserves a visibility check before
it is called a finding.

## Checker version

Established by running it, and it reverses the obvious choice:

| Version | One jar | 86–90 jars |
| --- | --- | --- |
| **1.8** (what Hadoop pins) | works, 62 s | **works** |
| 2.0 – 2.3 | works, 28 s | **deadlocks** |
| 2.4 (latest) | `ERROR: internal error in parser` | — |

2.4 fails under JDK 21 on a two-class toy jar, so it is not Hadoop-specific.

2.3 deadlocks for a specific, fixable reason. `Internals/APIDump.pm` runs javap
through `open3(*IN, *OUT, *ERR, @Cmd)` and the parser reads only `<OUT>`, never
draining `<ERR>`, with no `select()`. Once javap fills the 64 KB stderr pipe
buffer it blocks writing while perl blocks reading stdout. Observed directly:
perl in `anon_pipe_read`, javap's writer thread in `anon_pipe_write`, 29 minutes
elapsed on 22 seconds of CPU. 1.8 is immune because it does not use pipes at
all:

```perl
system($Cmd." ".$Input." >\"$Output\" 2>\"$TMP_DIR/warn\"");
```

Both streams go to files. So 2.x traded a robust design for a fragile one.

A one-line fix removes the third pipe, and is applied to our 2.3 checkout:

```perl
my $Pid = open3(*IN, *OUT, ">&STDERR", @Cmd);
```

Not yet verified at scale. **1.8 produced the results above** and remains the
version of record for this run.

### An Ozone-shaped POM: **a real finding**

The question that matters is answerable without building Ozone. Its
`hadoop-hdds/hadoop-dependency-client/pom.xml` excludes
`javax.servlet:javax.servlet-api` and `javax.servlet.jsp:*` from Hadoop and
declares its own servlet API. A POM mirroring exactly that pattern, resolved
against each ref, and every artifact carrying `javax/servlet/Servlet.class`
counted:

| Against | Artifacts providing `javax/servlet/Servlet.class` |
| --- | --- |
| trunk | 1 — `javax.servlet-api-3.1.0.jar` |
| **phase-c** | **2 — `jetty-servlet-api-4.0.9.jar` *and* `javax.servlet-api-3.1.0.jar`** |

**Correction: this probe was not Ozone-shaped enough.** Run against Ozone's
real dependency shape — 14 Hadoop artifacts and 19 exclusions rather than the 2
and 2 used here — the count is 1 on both refs, no change. Ozone's real
exclusions strip Hadoop's servlet API on phase-c as well. What follows describes
a mechanism that is real but that Ozone itself does not exhibit. On
trunk the exclusion matches, Hadoop's servlet API is removed, and the consumer's
own is the only one present. On phase-c the exclusion names a coordinate Hadoop
no longer ships, so it silently matches nothing, and two artifacts carrying the
same `javax.servlet` packages end up on one classpath. Maven reports no
conflict, because to Maven they are unrelated artifacts.

Which one wins is classpath-order dependent. The two are not equivalent —
`javax.servlet-api` 3.1.0 is Servlet 3.1, `jetty-servlet-api` 4.0.9 is Servlet
4.0 — so Jetty 12 ee8 code that expects Servlet 4.0 can meet the 3.1 classes
first and fail at runtime with `NoSuchMethodError`.

Two honest limits: this is a synthetic POM reproducing Ozone's exclusion
pattern, not Ozone's own build, so it demonstrates the mechanism rather than
proving Ozone breaks; and the same pattern in any downstream POM excluding
either old servlet coordinate has the same exposure.

This is also why rung 4 detects duplicate classes rather than unmatched
exclusions. An unmatched exclusion is common and usually harmless — what makes
this one matter is the second artifact that arrives in its place.

## Rung 6 — downstream compile: **a confirmed break**

Tez 0.10.4, `-pl tez-dag -am` (the core chain; `tez-ui`, `docs` and `tez-dist`
skipped, none on the HTTP path), built against each ref with
`-Dhadoop.version=3.6.0-SNAPSHOT`.

| Ref | Result | Wall clock |
| --- | --- | --- |
| trunk `d57814e3` | **BUILD SUCCESS** | 52 s |
| phase-c `91ccfd1f` | **COMPILATION FAILURE** | 32 s |

```
tez-common/src/main/java/org/apache/tez/common/web/ProfileOutputServlet.java:[21,33]
  package org.eclipse.jetty.servlet does not exist
tez-common/.../ProfileOutputServlet.java:[35,43] cannot find symbol
tez-common/.../ServletToControllerAdapters.java:[54,22] incompatible types:
  ProfileOutputServlet cannot be converted to javax.servlet.http.HttpServlet
```

### Why

`ProfileOutputServlet` extends Jetty 9's
`org.eclipse.jetty.servlet.DefaultServlet`:

```java
import org.eclipse.jetty.servlet.DefaultServlet;
...
public class ProfileOutputServlet extends DefaultServlet {
```

**`tez-common` declares no Jetty dependency.** Tez names Jetty in its POMs only
in exclusions — `org.eclipse.jetty:*` in three places and `jetty-util` in a
fourth. The `jetty-servlet` artifact that supplies `DefaultServlet` arrives
purely transitively from Hadoop. Rung 3 measured it leaving 34 module
classpaths, with `jetty-ee8-servlet` arriving in its place, and in Jetty 12 the
class is `org.eclipse.jetty.ee8.servlet.DefaultServlet`.

So the package disappears from Tez's compile classpath and the build stops.

### Assessment

This is exactly the failure HADOOP-19970 was predicted to cause — "anything
downstream that was getting one of those from Hadoop rather than declaring it
loses it silently" — and it is the first result in this run that is a real
downstream break rather than an explainable difference.

Two things make it notable:

* **No earlier rung caught it.** Rung 1 saw no reachable signature break; rung 2
  passed every invariant; rung 4 showed no change in Tez's servlet carrier
  count. The break is in an artifact leaving the closure, not in Hadoop's API
  and not in duplicate classes. Only compiling a real consumer found it.
* **It is downstream's to fix, but Hadoop causes it.** Tez should declare the
  Jetty it compiles against rather than borrowing Hadoop's. That does not make
  the breakage less real for anyone upgrading.

Whether this blocks HADOOP-19970 is a judgement call for reviewers. It is not a
Hadoop API break; it is a transitive dependency Hadoop is entitled to drop. But
it means the "invisible to downstream projects" claim is false as stated, and
the release note should say so.

## A second hazard: incoherent Jetty stacks

Every project that pins its own Jetty pins **Jetty 9**, while Hadoop moves to
12.0.37. Resolving each project's shape against both refs shows what that does.
Ozone is the clearest case, because on trunk it deliberately pins the exact
version Hadoop uses:

| | trunk | phase-c |
| --- | --- | --- |
| `jetty-server` | 9.4.58 | **9.4.58** |
| `jetty-io`, `jetty-http`, `jetty-security` | 9.4.58 | **9.4.58** |
| `jetty-servlet` | 9.4.58 | **absent** |
| `jetty-ee8-servlet`, `-nested`, `-webapp`, `-security` | absent | **12.0.37** |
| `jetty-client`, `jetty-ee`, `jetty-alpn-client` | 9.4.58 / absent | **12.0.37** |

On trunk Ozone has one coherent Jetty 9.4.58 stack. On phase-c it has **Jetty
12's ee8 modules layered on Jetty 9's core** — because it declares the core
artifacts directly, so nearest-wins mediates them down to 9.4.58, while the ee8
modules arrive only transitively from Hadoop at 12.0.37.

That stack cannot work. Jetty 12 rewrote the core `Handler`/`Request` model —
the same `HandlerWrapper` → `Handler.Wrapper` change rung 1 saw — so
`jetty-ee8-nested:12.0.37` against `jetty-server:9.4.58` is a
`NoSuchMethodError` waiting to happen. And `org.eclipse.jetty.servlet`, which
Ozone imports 18 times, is supplied by nothing at all in the phase-c column.

Knox, Hive, Spark and Atlas show the same 9-plus-12 split. They differ from
Ozone only in already having had two Jetty *patch* levels on trunk, which is
harmless; two *major* versions is not.

**Fidelity limit, stated plainly.** These probes model each project's Hadoop
dependencies and its declared Jetty artifacts. They do not model
dependencyManagement, profiles or parent POMs, and Maven mediation is sensitive
to exactly those. The pattern is consistent across five projects and the
mechanism is clear, but confirming it for any one project means building that
project. Ozone is the one to build.

## Ozone — compiles clean, then cannot load HttpServer2

The incoherent-stack hypothesis, tested against Ozone's real reactor rather
than a probe. `hadoop-hdds/framework` holds `BaseHttpServer`, which wraps
Hadoop's `HttpServer2`.

### Both refs compile

| Ref | Result |
| --- | --- |
| trunk | BUILD SUCCESS, 75 s |
| phase-c | **BUILD SUCCESS**, 62 s |

The probe's prediction that `jetty-servlet` would vanish was **wrong** — Ozone
declares it, so it stays, and Ozone's own source compiles.

### But the resolved classpath is incoherent

`dependency:list` on that module, real reactor, real dependencyManagement:

| Ref | Jetty artifacts |
| --- | --- |
| trunk | 9 artifacts, **all 9.4.58** — one coherent stack |
| phase-c | 9 artifacts at **9.4.58** (`jetty-server`, `-io`, `-http`, `-security`, `-servlet`, `-util`, `-webapp`, `-xml`, `-util-ajax`) **plus** 6 at **12.0.37** (`jetty-ee8-nested`, `-security`, `-servlet`, `-webapp`, `jetty-ee`, `jetty-session`) |

Ozone declares the Jetty 9 core artifacts directly, so nearest-wins keeps them
at 9.4.58, while Hadoop's ee8 modules arrive transitively at 12.0.37.

### And it fails at runtime

Loading Hadoop's `HttpServer2` on that exact classpath, 180 entries, taken from
Maven:

```
against trunk    HttpServer2 loaded from hadoop-common-3.6.0-SNAPSHOT.jar
                 all fields resolved — no linkage error

against phase-c  java.lang.NoClassDefFoundError:
                 org/eclipse/jetty/server/Deployable
```

`org.eclipse.jetty.server.Deployable` is a **Jetty 12** interface. Phase-c's
`HttpServer2` holds an `org.eclipse.jetty.ee8.webapp.WebAppContext`, which
implements it — but on Ozone's classpath `jetty-server` is 9.4.58, which has no
such type. The class cannot be linked.

**`BaseHttpServer` wraps `HttpServer2`, so every Ozone HTTP endpoint — SCM, OM,
Datanode, Recon, S3 Gateway — fails to start.** And because it compiles
cleanly, nothing catches it before deployment.

### Assessment

This is the most serious finding in the run, and more consequential than the
Tez break: a compile error is noticed immediately, whereas this ships.

The honest framing is that it is an **upgrade-path** failure. A downstream
project that bumps only `hadoop.version` to 3.6 and leaves its own Jetty at 9.x
gets a broken runtime. Ozone would presumably bump its Jetty too when adopting
Hadoop 3.6 — but it pins Jetty deliberately, currently to the exact version
Hadoop uses, and nothing in the upgrade tells it that pin has become fatal.

Reproduce with `bin/rung6-ozone.sh` and `consumer/RtProbe.java`.

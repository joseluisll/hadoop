Making Jetty 12 invisible to downstream consumers

A worked, tested attempt at relocating Jetty into a published hadoop-shaded-jetty artifact, so that Hadoop's container upgrade stops reaching downstream classpaths. What it fixed, what it broke, and what anyone repeating it should know before starting.

This work is stopped and is not proposed for merge. It was built against jetty-phase-c at 91ccfd1f; phases A, B and C have since been reworked, so the patch below no longer applies as-is. It is recorded here so the community can judge whether the approach is worth redoing on the new phase implementations — the findings and the defects it uncovered outlive the patch.

The problem

why any of this was needed

Upgrading to Jetty 12 on the ee8 environment breaks downstream projects, and mostly does so silently. Four projects were confirmed broken by real builds against phase-c:

ProjectFailureWhen it appears
Tez 0.10.4package org.eclipse.jetty.servlet does not existcompile
OzoneNoClassDefFoundError: org/eclipse/jetty/server/Deployableruntime, after a clean build
Hive 4.0.1sameruntime, after a clean build
Knox 2.0.0same, via gateway-spiruntime, after a clean build

The mechanism

Maven resolves one version per coordinate by nearest wins. A consumer that pins Jetty 9 declares org.eclipse.jetty:jetty-server at depth 1, so it beats Hadoop's transitive Jetty 12 at depth 2+. But Hadoop's org.eclipse.jetty.ee8:* coordinates are uncontested — the consumer has never heard of them — so they arrive at 12.0.37. The result is Jetty 9.4 core plus Jetty 12 ee8 on one classpath, and the ee8 classes reference Deployable, which 9.4 does not have.

This rules out every POM-level mitigation. No version, scope or ordering choice in Hadoop's POMs outranks a consumer's direct declaration. That is a property of Maven, not of this change, and it is why the work moved to relocation rather than dependency tuning.

Exposure is not predictable by reading a POM. Oozie pins Jetty 9.3.27 and comes through clean, because for Oozie the contested coordinates resolve to 12.0.37 through Hadoop and the stack stays coherent. What decides it is reactor-wide mediation depth. Every cheap static check tried during this work returned a false clean for every project that turned out to be broken.

The approach

hadoop-shaded-jetty

One new module publishes Jetty 12 ee8 pre-relocated under org.apache.hadoop.thirdparty.org.eclipse.jetty, with a dependency-reduced POM so no org.eclipse.jetty coordinate reaches consumers. Every Hadoop module that used Jetty imports from the relocated namespace instead. This is the pattern Hadoop already uses for Protobuf and Guava via hadoop-thirdparty.

Hadoop's Jetty and the consumer's Jetty then share neither a coordinate nor a package name, so Maven has nothing to mediate and the two implementations coexist as unrelated libraries.

The one boundary that matters

org.eclipse.jetty.toolchain — the servlet API — is deliberately not relocated and not bundled. This is forced, not stylistic:

You cannot relocate a type your callers implement. Downstream code writes implements AuthenticationHandler and extends HttpServlet. Rename those and no downstream class satisfies the clause any more. Relocation works for libraries you call; it fails for interfaces you expose. The rule the design encodes is: the container is Hadoop's private business, the spec is the public interface.

Why not the alternatives

OptionVerdictEvidence
Shade Jetty inside hadoop-common fails Works in isolation, fails three ways at reactor scale — WebApps handing an unshaded WebAppContext to a shaded server; websocket packages missing from the jar; WebServer needing a shaded context accepted by an unshaded API. Relocation is all-or-nothing across modules that interoperate.
Different container (Tomcat, Undertow) worse tomcat-embed-core bundles 88 servlet-spec classes inside its own jar — no coordinate to exclude, so it permanently collides with whatever downstream declares. Also removes the Jetty that Tez borrows, and is a rewrite of Hadoop's HTTP layer.
Mark Jetty provided/optional shifts cost No collision, but every project embedding HttpServer2 must declare exact ee8 coordinates itself, failing at runtime if wrong. Larger downstream ask than a pin bump.
Split API from implementation unprototyped Genuinely attractive and complementary. Hive and Knox reference HttpServer2 in 1 and 2 files respectively — they were collateral damage from a container they never embedded. Would not help Ozone (20 files).

Testing method

how the numbers were produced
  • Two refs, built identically into isolated local repositories — -Dmaven.repo.local per ref plus a shared read-only -Dmaven.repo.local.tail. Baseline is phase-c; candidate is phase-c plus the relocation patch. Nothing else differs.
  • -fae so a failing module does not stop the run, and -Dsurefire.rerunFailingTestsCount=0 so nothing is retried into passing.
  • Failing sets diffed by name, not by count. Matching totals are weak evidence — two different tests can fail on the two refs and still total the same. Every module's failures were compared as sets of test names.
  • target/classes and target/test-classes deleted per module per ref. Maven recompiles on changed sources, not changed dependencies; without this, stale classes link against jars that are gone. See Lesson 5.
  • Timed-out modules salvaged from surefire reports rather than discarded — the reports record exactly which classes completed, so a comparison over the classes both refs finished is still sound.

Scope of the comparison: the 27 testable modules the relocation patch touches. This is not all of Hadoop, and was never intended to be — modules the patch does not touch cannot be affected by it.

Defects found in the approach

the reusable part

Both defects share one shape, and it is the single most transferable thing in this document: relocation breaks things that refer to Jetty by name in text rather than in bytecode. Neither was visible to compilation, and one was invisible to 6,231 passing tests.

Defect 1 · packaging

Coordinate-based exclusions stop matching

hadoop-client-runtime and hadoop-client-minicluster exclude Jetty by groupId/artifactId. Once Jetty arrives as one pre-relocated artifact those excludes match nothing, and BanDuplicateClasses fails the build.

Fix: two added <exclude>org.apache.hadoop:hadoop-shaded-jetty</exclude> lines. Generalisation: audit every packaging rule that names Jetty by coordinate, not just these two.

Defect 2 · runtime · found late

Class names inside Jetty's own descriptors are not relocated

maven-shade-plugin rewrites class files and resource paths, but not class names inside resource content. Jetty names classes as text in webdefault-ee8.xml — the default web descriptor every WebAppContext reads:

<listener-class>org.eclipse.jetty.ee8.servlet.listener.IntrospectorCleaner</listener-class>
<servlet-class>org.eclipse.jetty.ee8.servlet.DefaultServlet</servlet-class>
<param-name>org.eclipse.jetty.session.SessionDomain</param-name>

After relocation those classes exist only under the thirdparty prefix. Jetty gets ClassNotFoundException, the context fails startup, and the webapp answers HTTP 503. Any Hadoop service hosting a UI from a directory would have returned 503 in production.

Caught by TestApplicationHistoryServer.testHostedUIs — and by nothing else. Compilation, both invariant checks, and 6,231 tests across three modules all passed over it.

Scope, measured rather than guessed. Of 40 resources in the jar still carrying unrelocated names, 36 are META-INF/maven/** build metadata and one is a GraalVM native-image config — none read at runtime. Four are functional: webdefault-ee8.xml and three configure_*.dtd.

Fix: a maven-antrun step after shade rewriting FQCNs in those four files, with org.eclipse.jetty.toolchain excluded and a negative lookbehind so a name is never prefixed twice. Verified: module went from 1 failure to 209 tests clean, class count unchanged.

Still unverified in the fix: the three configure_*.dtd rewrites were never exercised by any test — nothing in the suite parses Jetty XML config. And the 36 metadata files were left untouched by judgement, not by measurement of their harmlessness.

Lessons

for whoever redoes this

1 · Shading is not verified by compiling, and barely by unit tests

The strongest single finding here. The relocation passed compilation of all 119 modules, both invariant checks, and 6,231 tests — and still had a defect that would have returned 503 to every hosted UI. It surfaced only when a test started a real container and deployed a webapp from a directory. Any redo should treat "WebAppContext actually starts and serves" as a first-class gate, before the broad suites, not after.

2 · Relocation is all-or-nothing across interoperating modules

Shading Jetty inside hadoop-common alone works in isolation and fails three separate ways at reactor scale, because package names are the interface between modules — renaming one side renames half a conversation. A separate published artifact that every module imports from is the only shape that holds. This is why the hadoop-thirdparty pattern exists.

3 · Relocation cannot fix inheritance, and Tez is the proof

Tez's ProfileOutputServlet extends Jetty's DefaultServlet, borrowed from Hadoop's dependency closure. Moving that class puts it further out of reach, so shading makes Tez's diagnosis harder, not its problem smaller. The fix belongs in Tez and is two lines:

-import org.eclipse.jetty.servlet.DefaultServlet;
+import javax.servlet.http.HttpServlet;
-public class ProfileOutputServlet extends DefaultServlet {
+public class ProfileOutputServlet extends HttpServlet {

Verified safe by inspection: no super. call, no getResource, no ResourceService, no ContextHandler, and doGet overrides completely. This patch is correct independently of what Hadoop decides and is worth sending upstream regardless.

4 · Relocation changes a reachable signature, and it is not the one you would guess

HttpServer2.webAppContext the field is unreachable — final class, private constructor. But there is a public accessor, public WebAppContext getWebAppContext(), whose return type becomes a thirdparty type under relocation. Hadoop's own httpfs tests call it. HttpServer2 is @InterfaceAudience.Private so it is defensible, but it belongs in the release note, not in a downstream user's stack trace.

5 · Maven recompiles on changed sources, not changed dependencies

Comparing two refs by swapping -Dmaven.repo.local leaves the previous ref's compiled classes in target/. They link against jars that are no longer there and throw NoSuchMethodError, which reads exactly like a regression. This cost a full pass of the test run here: a test class compiled during an abandoned experiment surfaced as five errors naming org.apache.hadoop.shaded.… — a prefix the build under test never produces.

The tell is generalisable: if a class name in a failure cannot come from the ref you are testing, suspect the harness before the change. Delete target/classes and target/test-classes per module per ref, and audit with:

find <worktree> -name '*.class' -path '*/target/*' \
  -exec grep -l 'org/eclipse/jetty' {} + \
  | xargs grep -L 'org/apache/hadoop/thirdparty/org/eclipse/jetty'

6 · Cheap static checks were worse than useless here

Signature comparison, classpath scanning and POM inspection all returned a clean result for every project that turned out to be broken. Only real downstream builds found anything. Any redo should budget for real builds of Tez, Ozone, Hive and Knox rather than expecting a static gate to catch this class of break.

7 · Totals are weak evidence; diff the failing sets by name

Two different tests can fail on the two refs and still total the same. Every module here was compared as a set of failing test names, and timed-out modules were salvaged from surefire reports — which record exactly which classes completed — rather than discarded. That turned two apparently useless timeouts into real comparisons over 891 tests.

What was never established

open questions
  • Three modules were never tested — resourcemanager, hadoop-hdfs, mapreduce-client-jobclient. They are the largest suites and the run environment was reclaimed three times before reaching them.
  • The Oozie question. Oozie is green today because it takes jetty-server 12.0.37 through Hadoop. Relocation stops Hadoop contributing that, so Oozie falls back to its own 9.3.27 pin. Probably fine — its code targets 9.3 — but it was never tested, and projects that currently get their Jetty from Hadoop are exactly the population this fix could disturb.
  • No release-path leg. Everything compares trunk-to-trunk. The question a downstream user actually faces is upgrading from a 3.4.x release, and the servlet coordinate also moved once before this change.
  • Nine downstream projects is a sample, not proof. Since exposure depends on reactor-wide mediation rather than anything readable in a POM, four confirmed breaks is a lower bound. Atlas and Spark could not be tested at all.
  • Governance and release mechanics for a new published artifact were never addressed. The engineering is done; versioning and publication of hadoop-shaded-jetty are not.

Reproducing this

if the approach is revived
  1. Rebase the concept, not the patch. experiments/hadoop-thirdparty-jetty.patch (1,909 lines) targets phase-c at 91ccfd1f and will not apply cleanly to reworked phases. The module POM in experiments/hadoop-shaded-jetty.pom.xml is the reusable artefact — it carries both fixes and the reasoning as comments.
  2. Build two refs into isolated repositories and verify the worktree actually checked out (a build run from the wrong directory installs mislabelled artifacts and logs nothing unusual). RUNBOOK.md documents this and the other traps.
  3. Gate on a container-starting test first — deploy a WebAppContext from a directory and fetch a page. This is the check that would have caught Defect 2 in minutes rather than after three modules of clean suites.
  4. Then run the module suites with per-module target/ deletion, -fae, no reruns, and by-name failing-set diffs. experiments/remaining-suites.sh does this.
  5. Finally, real downstream builds of Tez, Ozone, Hive and Knox against both refs. This is the only step that ever found a downstream break.

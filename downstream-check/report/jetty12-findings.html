Does Jetty 12 break the ecosystem?

Yes, for four of the six projects that could be tested. Three of them build without a warning first.

Baseline trunk d57814e3 Candidate jetty-phase-c 91ccfd1f Covers HADOOP-19970 / 19971 / 19972

Verdict

Four confirmed downstream breaks, all reproduced by real builds: Tez fails to compile; Ozone, Hive and Knox compile cleanly and then cannot link Hadoop's HTTP stack.

The claim that this work is invisible to downstream projects is false. Whether that should block the change is a reviewer's decision — none of these are Hadoop API breaks, and two are arguably the downstream project's own fragility. But they are real, and a release note that does not mention them will surprise people.

Not universal, and the predicate is now known. Oozie pins Jetty 9 and comes through clean. What decides it is whether the project's own Jetty declaration wins Maven mediation for the core artifacts while Hadoop's ee8 modules arrive transitively — a property of declaration depth across the whole reactor, invisible from reading a POM.

Why three projects compile and then fail

The compile step passes because the project's own Jetty 9 jars satisfy every import in its source. The failure is one level down, in what Hadoop drags along beside them.

Estimated downstream impact

Confirmed broken

  • Ozone, Hive, Knox — compile clean, fail at runtime. Every HTTP entry point that goes through Hadoop's HttpServer2 fails to start. Nothing in the build warns them.
  • Tez — fails at compile. Loud and immediate, so lower risk in practice.

Who else is likely affected

  • Any project that declares jetty-server 9.x directly and takes Hadoop transitively. That is the predicate, and it is checkable in one command: resolve the classpath and see whether jetty-server lands at 9 or 12 while jetty-ee8-* is present.
  • Any project borrowing a Jetty jar it never declares. Tez's shape. Rung 3 measured jetty-servlet leaving 34 module classpaths, jetty-webapp 30, the websocket family 29 each.

Not affected

  • Shaded-client consumers. Packaging invariants unchanged; Spark is the notable case.
  • Projects with no Jetty imports — HBase, Ranger.
  • Projects whose Jetty declaration loses mediation — Oozie, which gets a coherent Jetty 12 stack.

Can it be made non-breaking?

The downstream fix is one line

Tested directly against phase-c, with a consumer taking hadoop-common and hadoop-hdfs:

Consumer's POMjetty-server resolves toJetty 12 ee8
pins Jetty 9.4.589.4.58fails
no Jetty pin at all12.0.37links
pins Jetty 12.0.3712.0.37links

Drop the pin, or move it to 12. Either works.

Hadoop cannot force it

Maven resolves one version per artifact by nearest wins. A consumer's direct declaration is depth 1; Hadoop's transitive Jetty is depth 2 or more. No version, scope or ordering choice in Hadoop's POMs outranks it. That is a property of Maven, not of this change — and it rules out any fix that works by adjusting Hadoop's dependency declarations.

Shading Jetty into hadoop-common — tried, and it mostly works

A maven-shade-plugin execution relocating org.eclipse.jetty into org.apache.hadoop.shaded.…, with createDependencyReducedPom. It builds clean in 47 seconds.

The consumer keeps its Jetty 9, Hadoop uses a private Jetty 12, and they no longer collide. That is the Ozone, Hive and Knox failure eliminated with no downstream change at all.

It does not fix Tez, and makes it worse. Tez borrows org.eclipse.jetty.servlet from Hadoop's closure. Against phase-c it inherits 13 Jetty jars but the class has moved to ee8; against the shaded build it inherits one, so it gets nothing at all. Three of four breaks fixed, the fourth left standing with a less obvious diagnosis.

What this proof of concept does not establish

  • Only hadoop-common was shaded. hadoop-hdfs, YARN and others use Jetty directly and cannot share its relocated copy, since the package names differ. Whether the full change is tractable is the open question.
  • 3 MB added per artifact that does this.
  • HttpServer2's API now exposes shaded Jetty types. It is Private, so defensible, but it is a signature change.
  • Untested: whether Hadoop's own modules still work against a shaded hadoop-common — the first thing a real attempt would need to prove.

And ee8 is not the problem

Choosing the ee8 environment is already the minimal-disruption option: it keeps the javax.servlet package names, where ee9 or ee10 would move the servlet API to jakarta.servlet and break every consumer's imports outright. What breaks things here is Jetty 12 relocating its own core packages — Deployable, Handler.Singleton — which no environment choice avoids.

How to read this

Every number is a difference between two Hadoop refs built identically, minutes apart, into isolated local repositories. A check that fails the same way on both sides is reported as telling us nothing — Atlas and, before its probe was fixed, Oozie.

Nine projects is a sample, not proof, and three of them could not be tested at all. Of the six that could be, four break. The cheap checks were not merely incomplete — they were actively misleading, returning a clean result for every project that turned out to be broken.

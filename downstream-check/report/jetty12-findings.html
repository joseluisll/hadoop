HADOOP-19912 · conclusions · 2026-08-25

Jetty 12 breaks four downstream projects. Three can be fixed inside Hadoop.

Nine ecosystem projects examined, six testable, four broken by real builds. A hadoop-thirdparty-style relocation removes three of them with no downstream change and no test regressions. The fourth needs two lines in Tez.

Bottom line

The migration is not invisible downstream — but it also does not have to be a breaking change. Both halves of that were established by building things, not by reading POMs.

The break is real and mostly silent: three of the four projects compile cleanly and fail at class-load time. The fix is real too, and it is a known Hadoop pattern rather than a workaround. What remains is a scope decision for reviewers: the fix is 74 files and a new published artifact, and it has been validated on three modules, not on all of Hadoop.

Conclusions

what is now settled

The change breaks downstream projects, and the failure is usually silent until runtime.

Tez fails to compile. Ozone, Hive and Knox compile without a single warning and then throw NoClassDefFoundError: org/eclipse/jetty/server/Deployable when Hadoop's HTTP stack is first touched. A downstream project's green build says nothing about whether it survives this.

Real builds of each project against both Hadoop refs, minutes apart, into isolated local repositories.

Exposure is not predictable by reading a POM.

It is not "any project that pins Jetty 9" — Oozie pins 9.3.27 and comes through clean. The failure needs the project's own Jetty declaration to win Maven mediation for the core artifacts while Hadoop's ee8 modules arrive transitively. That is a property of declaration depth across an entire reactor, which is why every cheap static check returned a false clean.

Oozie disproves the simple predicate; classpath composition measured per project.

Hadoop cannot fix this by changing its dependency declarations.

Maven resolves one version per artifact by nearest wins. A consumer's direct declaration is depth 1; Hadoop's transitive Jetty is depth 2 or deeper. No version, scope or ordering choice in Hadoop's POMs outranks it. This rules out the entire class of POM-only mitigations before they are attempted.

Property of Maven mediation, confirmed against the built refs.

Relocating Jetty into a published artifact does fix it — three of the four, with zero downstream action.

A new hadoop-shaded-jetty module publishes Jetty 12 ee8 pre-relocated under org.apache.hadoop.thirdparty.…; the servlet API is deliberately left unrelocated, because that is what downstream code compiles against. The consumer keeps its Jetty 9, Hadoop uses its own Jetty 12, and the two never meet. Ozone, Hive and Knox are fixed at the source.

Built and measured: consumer classpath carries Jetty 9.4 only; HttpServer2 loads.

Tez is a separate problem, and shading makes it harder, not easier.

Tez's ProfileOutputServlet extends Jetty's DefaultServlet, borrowed from Hadoop's dependency closure. Inheritance cannot be satisfied by relocation — moving the class puts it further out of reach. The fix belongs in Tez and is two lines.

Confirmed by inspection: the class uses nothing from DefaultServlet.

The ee8 environment is the right choice and is not the cause.

ee8 keeps the javax.servlet package names; ee9 or ee10 would move them to jakarta.servlet and break every consumer's imports outright. What breaks here is Jetty 12 relocating its own core — Deployable, Handler.Singleton — which no environment choice avoids. Reverting to ee9/ee10 would be strictly worse.

Package-level comparison of the Jetty 9.4 and 12.0 ee8 artifacts.

The Tez fix

-import org.eclipse.jetty.servlet.DefaultServlet;
+import javax.servlet.http.HttpServlet;

-public class ProfileOutputServlet extends DefaultServlet {
+public class ProfileOutputServlet extends HttpServlet {

No super. call, no getResource, no ResourceService, no ContextHandler, and doGet overrides completely. The class never used anything a DefaultServlet provides.

One trap worth carrying forward

Packaging rules that name Jetty by coordinate stop working. BanDuplicateClasses failed on the first relocated build because hadoop-client-runtime and -minicluster exclude Jetty by groupId/artifactId, and those excludes no longer match once Jetty arrives as a single pre-relocated artifact. Two added <exclude> lines fix it — but every such rule needs the same review.

Caveats

what this does not establish
  • Three modules were tested, not all of Hadoop. hadoop-auth, hadoop-common and hadoop-yarn-common — chosen because they hold the migration's surface, HttpServer2, and WebApps. HDFS, the YARN servers, MapReduce, the cloud connectors and the client-module integration tests were not run; they need clusters this environment does not have.
  • HttpServer2's API now exposes org.apache.hadoop.thirdparty… Jetty types. It is @InterfaceAudience.Private, and Hadoop accepted the same trade for Protobuf, but it is a real signature change and someone is compiling against it.
  • The fix adds a published artifact, with the release process that implies. The engineering is done; the versioning, publication and governance around a new hadoop-shaded-jetty are not part of what was demonstrated.
  • Three projects could not be tested at all. Atlas fails on both refs (Jersey 1 is already gone from trunk, unrelated to Jetty), and Spark consumes shaded clients, so the probe overstates its exposure. Their status is unknown, not clean.
  • Nine projects is a sample. Since exposure depends on reactor-wide mediation rather than anything readable in a POM, the four confirmed breaks are a lower bound.
  • No 3.4.x leg was run. The question a downstream user actually faces is upgrading from a release, and the servlet coordinate also moved once before this change.
  • Signature comparison catches signatures only. A method that still exists but dispatches differently is invisible to it.

Claims that did not survive checking

Recorded so none of them resurfaces as received wisdom.

ClaimedActually
Any project pinning Jetty 9 is exposed. Oozie pins 9.3.27 and is fine. Mediation decides, not the pin.
Shading hadoop-common alone is a workable route. Fails three ways at full-reactor scale. Package names are the interface, so relocation is all-or-nothing across modules that interoperate.
HttpServer2.webAppContext is a downstream-reachable break. Unreachable — final class, private constructor.
HBase is the strongest detector to prioritise. Zero Jetty imports. It cannot detect this at all.

Recommended

for reviewers
  • Do not ship phase-c as-is on the claim that it is downstream-invisible. That claim is disproved by four real builds.
  • Take the relocation, or accept the break knowingly. Those are the two honest options. There is no POM-level middle ground — Maven's mediation rules it out.
  • If the relocation goes forward, run the remaining suites first. HDFS, the YARN servers and the client-module integration tests are the gap between what has been shown and what a merge needs.
  • Either way, the release note must name the failure mode. A NoClassDefFoundError on org/eclipse/jetty/server/Deployable after a clean build is not something a downstream maintainer will diagnose quickly on their own.
  • Send the two-line patch to Tez regardless. It is correct independently of what Hadoop decides, and Tez should not be extending a Jetty class it does not use.
Every number is a difference between two Hadoop refs built identically, minutes apart, into isolated local repositories; a check failing the same way on both sides is reported as telling us nothing.
